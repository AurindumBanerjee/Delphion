The Gradio Monolith

One process, one UI, one Chroma collection held in session memory. The first version of Delphion that actually answered a question about a PDF — and the last one that cost money every time it did.

The shape of it

Everything happened inside a single Python process. There were no services, no queues, no network hops. An upload handler built a vector index and handed the live object back to Gradio, which kept it in per-browser session state; a message handler took that same object, searched it, and called OpenAI.

Two paths, meeting at one piece of state:

The detail that mattered ./chroma_db was written to disk, but nothing ever read it back. The collection object returned into gr.State was the real source of truth. Refresh the page and your documents were gone. This was harmless here — and became the defining bug of v2, where the same on-disk index was suddenly expected to be shared across containers.

ui.py — the whole application

139 lines of gr.Blocks. The interesting part is not the layout but how state moved through it.

collection_state = gr.State(None)

def process_upload(files, method, c_size, c_overlap):
    collection = load_documents(files, chunking_method=method,
                                chunk_size=c_size, chunk_overlap=c_overlap)
    return collection, "Successfully processed…"   # ← object into state

file_output.upload(
    fn=process_upload,
    inputs=[file_output, chunking_method, chunk_size, chunk_overlap],
    outputs=[collection_state, upload_status],     # ← stored per session
)

Returning a live Python object as a Gradio output is what put the Chroma handle in session state. It is an elegant trick and the reason this version needed no database wiring at all.

The message path is symmetrical, and uses a small idiom worth keeping:

def process_message(message, history, collection, sys_prompt):
    if not message.strip():
        return history, ""
    updated_history = predict(message, history, collection, sys_prompt)
    return updated_history, ""     # empty string clears the textbox
Latent crash The UI forwarded chunk_size and chunk_overlap to every chunker via the factory, but markdown_header_chunk_documents(documents, headers_to_split_on=None) accepted neither. Selecting markdown raised TypeError. It went unnoticed because nobody chose that option.

predict.py — the entire RAG loop

Sixty-seven lines, of which about fifteen matter:

context_chunks = collection.similarity_search(message, k=3)
context_text = "\n\n".join([doc.page_content for doc in context_chunks])

client = OpenAI()
completion = client.chat.completions.create(
    model="gpt-3.5-turbo",
    messages=[
        {"role": "system", "content": system_prompt},
        {"role": "user",
         "content": f"Question: {message}\n\nContext: {context_text}"},
    ],
)
reply = completion.choices[0].message.content

Retrieve three chunks, flatten them into one string, paste into a prompt. That is the whole thing, and for a first version it is the right amount of code. What it could not do is explain itself.

Citations were structurally impossible The default system prompt asked the model to “cite the relevant section or page if possible”. But the chunks were joined into one undifferentiated blob with no source or page markers — the model had nothing to cite with. The metadata existed: load_documents assembled source, author, title, creation date and page number into all_metadatas, then passed LangChain’s defaults to the store instead and threw its own work away.

The two dead files

Both are kept because they show the iteration, not because they ran.

chunking.py

Twelve lines: a bare CharacterTextSplitter at 500/50. Never imported by the factory. Superseded before this version shipped.

semantic_chunking.py

An earlier semantic chunker — CharacterTextSplitter first, then SemanticChunker over the result, on text-embedding-ada-002. Also never imported: the factory pulled semantic_chunk_documents from advanced_chunking.py, which used text-embedding-3-small.

Two functions, one name semantic_chunk_documents existed in two modules with different signatures and different embedding models. Only one was reachable. This is the kind of ambiguity that costs an hour of debugging six months later, and it is why both files were deleted rather than fixed in the current version.

What it cost

Every upload paid OpenAI proportional to document length. Every question paid twice — once to embed the query, once to generate the answer. The chunk embedding cost scaled with the corpus; the query cost scaled with traffic.

CallModelFrequency
Chunk embeddingtext-embedding-3-large once per chunk, per upload
Semantic chunkingtext-embedding-3-small once per sentence, if selected
Query embeddingtext-embedding-3-large once per question
Generationgpt-3.5-turbo once per question

This is the reason the project moved on. Not that it was expensive to run personally — it wasn’t — but that publishing it meant paying for every visitor’s curiosity, which made it undeployable.

What it got right Session-scoped state via gr.State was the correct instinct, and the current version came back to it. The chunking factory was a clean abstraction. The system prompt was well written — grounded, with an explicit refusal string. The bones were sound; the economics weren’t.

Where it went

v2 split the monolith into embedder / retriever / generator services on Modal, to make the expensive parts independently scalable. It introduced a worse bug: the on-disk Chroma index that v1 never relied on suddenly had to be shared across autoscaled containers, and wasn’t.

v3 — the current root application — returned to a single process and to session-scoped state, but replaced OpenAI embeddings with a local ONNX model running in-process and made the index explicitly in-memory. It keeps v1’s simplicity and drops v1’s bill.
