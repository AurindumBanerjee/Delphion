The Modal Service Split

Three FastAPI applications — embedder, retriever, generator — mounted under one ASGI app and deployed to Modal. The decomposition was right. Putting a database inside disposable compute was not.

Naming The mcp/ folder predates and has nothing to do with the Model Context Protocol — it stood for “micro-service components”. The name is a real hazard: mcp is now a package on PyPI, and from mcp.embedder import app would collide with it. Renaming was on the list when this version was retired.

The shape of it

A Gradio page running locally made three HTTP calls to a Modal deployment. Inside that deployment, one FastAPI() instance mounted three sub-applications, each owning one stage of the pipeline. Modal built the container image by cloning the repository from GitHub at build time, injected the OpenAI key from a secret, and autoscaled containers under load.

The failure, precisely

Chroma persisted to ./chroma_db — a path on the local filesystem of whichever container happened to serve the request. Modal was configured with @modal.concurrent(max_inputs=100) and autoscaled freely, and containers are reclaimed when idle.

So an upload built an index in container A, and the next question routed to container B, which had an empty folder and returned nothing. Nothing in the application code was wrong. The architecture guaranteed the failure.

Compounded at retriever.py line 6 
app = FastAPI()
collection = get_chroma_collection()   # runs at import — container boot

The collection handle was bound once when the container started and never refreshed, so even writes made by the same container after boot were not reliably visible.

This is the lesson the current version is built around: stateful storage does not belong inside stateless compute. The fix was never a code change — it was either moving the index out of the container, or stopping using many containers.

stub.py — the deployment

Fifty-one lines that describe the whole environment. The build strategy is the part worth studying, because it shaped everything about the workflow.

image = (
    modal.Image.debian_slim(python_version="3.10")
    .apt_install("git")
    .run_commands(
        f"echo rebuild-trigger-{modal.__version__}",  # forces rebuild
        "rm -rf Delphion",
        f"git clone {GITHUB_REPO}",
        "pip install uv",
        "uv pip install --system -r Delphion/requirements.txt",
    )
)

The application code was baked into the image at build time, by cloning from GitHub. Three consequences followed:

  • You could only deploy code already pushed to main. Local edits were invisible to the deployment, so there was no fast local loop.
  • Docker layer caching reused a stale clone when the command was unchanged, so a fresh push produced no change — hence the echo rebuild-trigger-… line, which exists purely to bust the cache.
  • Every deploy was a full image rebuild and dependency reinstall, making the edit → test cycle minutes long.

Inside the container, fastapi_app() asserts the key injected by modal.Secret.from_name("delphion-secret"), appends /Delphion to sys.path, imports the three sub-apps and mounts them.

Doubled path segments A sub-app mounted at /embed whose own route is also /embed is reachable at /embed/embed. Both clients hardcode this shape. Harmless, but it reads as a mistake to anyone opening the URL list cold.

The three services

embedder.py — ingestion

POST /embed, multipart: files[] plus form fields for chunking method, size and overlap. The most carefully written file in this version:

clean_name = os.path.basename(file.filename)
filename = f"{uuid.uuid4()}_{clean_name}"
file_path = f"/tmp/{filename}"
Genuinely good defensive code os.path.basename strips any ../ path-traversal attempt from a client-supplied filename, and the UUID prefix prevents collisions between up to 100 concurrent requests sharing one container’s /tmp. Most portfolio code ignores both risks.

It then reports the chunk count by reaching into Chroma’s private internals:

count = 0
try:
    count = collection._collection.count()   # private API
except Exception:
    pass                                     # ← silently reports 0

A bare except: pass around a private attribute means any upstream library change silently reports zero chunks — and the response then claims "embedding failed" regardless of whether embedding worked.

retriever.py — search

The smallest and cleanest file: twenty-seven lines, a Pydantic RetrieverInput(input: str, k: int = 4), a similarity_search, and a response carrying both a joined string and a structured list of chunks with metadata.

Good API design Returning {"output": "…", "chunks": [...]} lets a simple client render the string and a richer one use the structure. That dual shape carried forward into the current version’s cited-passages panel.

Its only flaw is the import-time binding described above.

generator.py — never implemented

This file is a copy of embedder.py It defines POST /embed, saves uploads, and calls load_documents. It contains no LLM call of any kind. Mounted at /generate, the endpoint the UI actually called — POST /generate/generate — did not exist and returned 404.

So the “Generator” box in both clients always showed "No generator output", and there was no retrieve → generate pipeline at all. A user retrieved passages into one textbox and would have had to paste them into another by hand. The RAG loop was open in this version; the only working end-to-end path was still v1’s predict.py, which this version didn’t use.

It also regressed the embedder’s filename handling, writing to /tmp/{file.filename} with no basename and no UUID — reintroducing both the traversal and the collision risk that embedder.py had fixed.

Request traces

Uploading a PDF

  1. app.py:upload_pdfs opens each Gradio temp file and POSTs multipart to {BASE_API}/embed/embed.
  2. Modal routes to some container; FastAPI dispatches to embedder.embed.
  3. Files are written to /tmp/{uuid}_{name}.
  4. load_documents() → PyMuPDFLoader → one Document per page.
  5. ChunkingFactory.create_chunker(...) returns a lambda; calling it produces chunks.
  6. create_vectorstore() → OpenAIEmbeddings (text-embedding-3-large) → Chroma.from_texts(persist_directory="./chroma_db").
  7. collection._collection.count() → {"status": "embedding complete", "chunks": N}.

Asking a question

  1. app.py:ask_question POSTs {"input": q, "k": k} to /retriever/retriever.
  2. Modal routes to a container — possibly a different one.
  3. retriever.retrieve uses the module-level collection bound at that container’s boot.
  4. If that container never handled the upload, the folder is empty, similarity_search returns [], and the UI shows nothing.

Step 4 is where this version died.

What it got right

Worth recording
  • The service boundaries were correct — embed / retrieve / generate is the right decomposition of a RAG system.
  • Secret injection via Modal was the proper way to handle the API key: never in the repo, never in the image.
  • The retriever’s dual string-plus-structured response was a thoughtful API.
  • The embedder’s filename sanitisation showed awareness of a bug class most projects never consider.
  • It deployed — a build image, a secret, a public URL. That is a real step past “runs on my laptop”.

Why it was replaced

The bug was not fixable in code. It required either moving the index out of the container — a hosted vector database or an attached volume — or not using many containers.

With no budget and no requirement for persistence, the current version takes the second path: one process, one in-memory index scoped to a browser session, on a free Hugging Face Space. Embeddings moved to a local ONNX model, so the high-volume call costs nothing; generation points at any OpenAI-compatible endpoint. And the job this version started — an actual generator, wired to retrieval — is finally finished.
